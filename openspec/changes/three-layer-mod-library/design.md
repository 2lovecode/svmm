## Context

当前实现把模组直接放在游戏 `Mods/`，方案组（`domain/profiles.rs`）只保存 `enabledModIds`，应用时对目录做启用/禁用差异。Nexus 下载与 zip 导入的目标也是游戏 `Mods/`。

本变更把数据分成四段：Nexus 远程目录、本地库（包）、方案组（名单）、游戏 `Mods/`（应用结果）。玩家改过的模组文件放在按 UniqueID 共享的用户数据里，应用时先收再盖。

约束：UI 只通过 Tauri 命令改磁盘；星露谷存档不在 `Mods/`，不纳入本流程；第一版用文件复制部署，不用硬链接。

## Goals / Non-Goals

**Goals:**

- 下载与导入只写本地库。
- 方案组是本地库 UniqueID 的名单；应用 = 收用户数据 → 清空玩家模组 → 复制包 → 盖回用户数据。
- 首页是不可删除的默认方案组，并显示是否已应用到 `Mods/`。
- Nexus 列表状态对照本地库：未下载 / 已有 / 有更新。

**Non-Goals:**

- 同一模组在不同方案组使用不同配置。
- 本地库同时保留同一模组的多个版本。升级和降级都是替换当前这一份，不并存。
- 用启用/禁用后缀管理方案组。
- 硬链接或联接部署。

## Decisions

### 1. 本地库存一个当前包

路径：`app_data_dir()/library/<unique-id>/`，内含包文件和 SVMM 写入的清单（相对路径 + 内容哈希）。更新时整目录替换为新包并重写清单。

同一 UniqueID 再次导入视为替换当前包，不并存两份。没有 `manifest.json` 的 UniqueID 时，用稳定的文件夹名作为库键，并在界面上与真正的 UniqueID 区分。

降级不在磁盘上留旧包。系统向 Nexus 列出该模组的历史文件，用户选定一个后下载并替换当前包。替换后若该包不是 Nexus 最新文件，目录状态为有更新。

备选：按版本分子目录并存，方案组各自指向一版。拒绝原因是已确认不做多版本共存；方案组只记 UniqueID，并存会让「当前用哪一版」产生歧义。

### 2. 部署用复制，不用硬链接

应用时把库中的包复制到 `Mods/<文件夹名>/`。复制使库目录和游戏目录各有一份文件，换版本时可以分别备份、失败时分别还原。

备选：硬链接省空间。拒绝原因是替换库文件会破坏或意外改写已部署目录。

### 3. 用户数据按 UniqueID 共享

路径：`app_data_dir()/userdata/<unique-id>/`。

收取规则：对当前 `Mods/` 里每个能对应到本地库的模组，遍历文件；相对路径不在清单中，或哈希与清单不同，则复制到用户数据。`config.json` 只要与清单哈希不同就一定收取。

盖回规则：包复制完成后，把该 UniqueID 的用户数据文件覆盖到部署目录。同路径以用户数据为准，因此玩家的 `config.json` 压过新包里的模板。配置迁移仍由模组自己负责。

删除本地库模组时不删用户数据，以便再次下载后配置还在。

备选：按方案组隔离用户数据。拒绝原因是已确认配置跟着模组走；隔离留到以后的显式开关。

### 4. 应用前先做 Mods 备份，失败则还原

在改动 `Mods/` 之前，把将被删除的玩家模组目录复制到临时备份。清空与复制任一步失败，则删掉本次已写入的玩家模组并还原备份。成功后删除备份。SMAPI 自带目录不进入备份、也不删除。

### 5. SMAPI 自带模组排除在库和方案组之外

固定排除目录名：`ConsoleCommands`、`ErrorHandler`、`SaveBackup`。实现时用当前 SMAPI 包内这三个 `manifest.json` 的 UniqueID 再对一次，避免只靠文件夹名。扫描、入库、方案组勾选、应用清空都跳过它们。

### 6. 「已应用」用 ID 集合加版本比较

不把游戏目录当作名单来源。比较时忽略上述 SMAPI 目录：`Mods/` 中的 UniqueID 集合等于方案组名单，且每个模组的 manifest 版本等于本地库当前版本，才算已应用。

### 7. 换版本同步已部署副本

方案组只存 UniqueID，所以更新或降级之后，所有包含该模组的方案组展示的都是本地库里这一份当前包。

若该 UniqueID 当时在游戏 `Mods/` 中，紧接着做单模组同步，不整组重应用：

1. 新包先下载到临时目录。
2. 备份当前库目录，以及 `Mods/` 中该模组目录。
3. 用新包替换库目录并重写清单。
4. 按旧清单收取该部署目录的用户数据，用新包替换部署目录，再盖回用户数据。
5. 任一步失败：库目录和部署目录都回到备份，临时新包删除。
6. 该 UniqueID 不在 `Mods/` 中则只替换库，不改游戏目录。

### 8. 旧数据迁移

启动时若发现游戏 `Mods/` 里有非 SMAPI 模组、且本地库为空：

- 将这些目录复制进本地库（不移动，避免迁移失败弄丢游戏里的模组）。
- 清单按复制当时的全部文件生成。
- 若存在 `config.json`，同时复制一份到用户数据。
- 启用中的模组加入默认方案组；带禁用标记的只入库、不进默认组。
- 旧 `profiles/*.json` 的 `enabledModIds` 若能在本地库找到对应 UniqueID，转成新名单；找不到的 ID 丢弃。无法转换的文件保留备份后不再当作方案组读取。

## Risks / Trade-offs

- [应用会删除不在方案组里的玩家模组] → 应用前备份，失败还原；迁移时复制而不是移动。
- [用户改过的包内文件会被当成用户数据永久盖回，可能挡住上游文件更新] → 只对哈希不同的文件收取；在风险说明中接受 `config.json` 以玩家为准。
- [模组把数据写到 `Mods/` 之外的未知路径] → 不处理。存档与 `WriteSaveData` 本来就不在 `Mods/`，不受应用影响。
- [中途崩溃留着半份 Mods] → 备份目录放在应用数据下，下次启动若发现未完成标记则还原。
- [换版本时库已替换但部署目录写到一半] → 单模组备份；失败时库和部署一起回到替换前。
- [旧方案组模型不兼容] → 一次性迁移，见决策 8。

## Migration Plan

1. 先落库路径、清单与入库命令，旧的「直接装进 Mods」命令改为入库。
2. 再落用户数据收取/盖回与应用事务（含备份）。
3. 最后改首页、浏览页、方案页。
4. 回滚：本变更上线前的 `Mods/` 仍是完整副本（迁移不删除它）。若需放弃新模型，停止调用新的应用命令即可，游戏目录保持迁移前的内容，直到用户成功应用过一次。

## Open Questions

- 无。配置跨方案组共享、复制部署、单版本替换（含降级到 Nexus 历史文件）均已确认。SMAPI 三个自带模组的 UniqueID 在实现时对照随包 manifest 填写，不改变本设计。
